# 任务3-启动优化，替换接口

旧版接口，只能获取总微博数，然后依靠页码获取分页。但代价是一旦发了新微博，旧页码就会失效，同时也不方便故障后的任务重试。

新微博接口提供了按日期检索功能，可以从2009年9月1日开始，一直搜索到今天。据此可以建立任务抓取流程

- 先按年份进行搜索，每年搜索1次，根据`data.total`字段得到当年发微博总数
  - 若微博数为0，则该年份不需要检索，标记为抓取成功后，跳过
- 若微博数大于0，则按月搜索，根据`data.total`字段得到当月发微博总数
  - 若微博数为0，则该月份不需要检索，标记为抓取成功后，跳过
- 若微博数大于0，则从当月1日0点0分开始，每7天一个时间段，检索到7日后23:59:59，得到当周发微博总数. 若跨周，则只检索到本月最后一天即可。
  - 若微博数为0，则该周不需要检索，标记为抓取成功后，跳过
  - 若微博数大于0，则开始按page参数从1开始进行检索，每次返回50条，可据此计算需要查询至第多少页
    - 进行抓取
    - 存入数据库
    - 标记任务是否成功

需要做的事情是：

1. 根据微博返回值，建立数据模型，用于验证接口字段是否正确(可用zod)
2. 根据现有代码，将旧接口返回值和输出html进行隔离，方便在替换接口时不影响输出实现
3. 根据新接口返回值，对接html输出
   1. 新接口返回当前用户有阅读权限的微博记录，但不超过50条
4. 建立抓取任务体系。同时gui界面上也要予以反应，方便大家了解进度，进行重试.
   1. 如果抓取时间范围距现在1个月以上，应对接口返回值建立缓存。当请求成功时，用json记录下该参数对应的返回值，不设有效期。这样重跑时只要读取缓存即可。缓存开关需要在前端明确列出，允许清除缓存，或者不使用缓存，重新抓取
5. 为避免被微博反爬识别，所有对微博服务器的请求都要有延迟，原则是每10s只能发出1个请求。可以据此估计抓取总耗时，x1.5后作为预计时间(渲染也需要时间)。

@todo(worker)
